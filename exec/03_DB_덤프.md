# 3. DB 덤프

## 대상

서비스 DB는 **MySQL 8.0, 데이터베이스 `news`** 하나다. B 서버 컨테이너 `news-mysql`.

| 표 | 내용 | 행 수 · 크기 (2026-09-23 실측) | 정의 |
|---|---|---|---|
| `article` | 기사 (Kafka `news.article.raw`로 적재) | **9,341,199 · 4,955 MB** | `back/.../article/domain/Article.java` |
| `issue` | 이슈 (Kafka `news.clustering.completed`로 갱신, key=clusterId) | 3,945 · 1.6 MB | `back/.../issue/domain/Issue.java` |
| `issue_common_facts_briefing` | 이슈별 공통사실 문장 (Issue의 컬렉션 표) | 6,020 · 4.0 MB | `Issue.java` `@ElementCollection` |
| `viewpoint_group` | 이슈 안 관점 그룹 | 11,678 · 3.0 MB | `back/.../viewpointgroup/domain/ViewpointGroup.java` |

스키마는 JPA `ddl-auto: update`가 만든다. 별도 DDL 파일은 없다.

계정(실측 `mysql.user`): `news@%`(앱), `root@%`·`root@localhost`(관리), `exporter@%`(모니터링, `back/docker/mysql/init/01-exporter-user.sql`). 비밀값은 `back/deploy/docker-compose.infra.yml`.

## 덤프 파일 위치

**`exec/db/news_dump_2026-09-27.sql.gz` (1.5 MB, 2026-09-28 00:57 KST 생성)** — 표 4개 스키마 전부 + `issue`·`issue_common_facts_briefing`·`viewpoint_group` 데이터. `article` 데이터 제외. 파일명 날짜는 B 서버 시간대(UTC) 기준이다.

**전체 덤프는 불가능하다.** `article`만 4.9 GB라 제출 한도 100 MB를 50배 넘는다. 아래처럼 **기사 표는 스키마만, 나머지 세 표는 데이터까지** 담으면 10 MB 안쪽이다.

## 생성 (B 서버에서)

```bash
cd ~/news-platform
DATE=$(date +%F)
{
  # 1) 네 표 전부 스키마만
  docker exec news-mysql sh -c 'exec mysqldump -unews -p"$MYSQL_PASSWORD" --no-data --no-tablespaces --set-gtid-purged=OFF news'
  # 2) 기사 표를 뺀 세 표는 데이터까지
  docker exec news-mysql sh -c 'exec mysqldump -unews -p"$MYSQL_PASSWORD" --no-create-info --no-tablespaces --single-transaction --quick --set-gtid-purged=OFF \
      --ignore-table=news.article news'
} | gzip > news_dump_${DATE}.sql.gz
ls -lh news_dump_${DATE}.sql.gz     # 수 MB 여야 정상
```

`MYSQL_PASSWORD`는 컨테이너 환경변수에 이미 있어 셸에 노출하지 않고 쓸 수 있다. `--no-tablespaces`는 `news` 계정에 `PROCESS` 권한이 없어 넣는다(없으면 tablespace 덤프 오류가 찍히지만 결과 파일은 정상).
파일을 로컬로 받아 `exec/db/`에 두고 커밋한다(`scp -i J15E105T.pem ubuntu@j15e105.p.ssafy.io:~/news-platform/news_dump_*.sql.gz exec/db/`).

기사 데이터가 필요하면 최근 며칠만 따로: `--where="published_at >= DATE_SUB(NOW(), INTERVAL 3 DAY)" news article` (컬럼명은 `Article.java` 확인). 복원 뒤 화면을 채우는 다른 길은 DE가 `PUBLISH_MODE=send`로 이슈 피드를 다시 발행하는 것이다 — `article`은 크롤러가 15분마다 다시 채운다.

## 복원

```bash
# 빈 MySQL 컨테이너가 떠 있고 DB news 가 있는 상태에서
gunzip -c news_dump_<날짜>.sql.gz | docker exec -i news-mysql sh -c 'exec mysql -unews -p"$MYSQL_PASSWORD" news'
```

복원 뒤 앱을 기동하면 `ddl-auto: update`가 덤프 시점과 현재 엔티티의 차이를 맞춘다(컬럼 추가만 자동, 삭제·타입 변경은 수동).
모니터링 계정은 덤프에 포함되지 않으므로 `01-exporter-user.sql`을 한 번 더 실행한다.

## 덤프 대상이 아닌 저장소

| 저장소 | 이유 | 재생성 |
|---|---|---|
| Airflow 메타 DB (A, PostgreSQL 16) | 실행 이력·연결 정보만. 데이터 아님 | 컨테이너 재생성 후 `airflow pools set spark_local 1 …` 1회 |
| Pinpoint MySQL·HBase (A) | 트레이스 저장소 | 없어도 서비스 무관 |
| HDFS `/lake` (A, 약 190GB) | DB가 아닌 데이터 레이크. bronze(원본)·silver(정제)·gold(피드) | `data/de/docs/lake-layout.md`, 백업·복구는 `data/de/docs/backup-restore.md` |
| DS `~/gold` (A) | 군집 중간·결과 산출물 | `ds_input`에서 체인 재실행 |
| Redis (B) | 캐시. 재시작 시 앱이 다시 채움 | 자동 |
| Kafka (B) | 보관 7일 메시지 큐 | 재생성 시 DE에 알림(체크포인트) |
